# Lesson — Read Before Assessing

## The Pattern

When DAF shared the Bursa POC email thread, I immediately built a 38% readiness assessment, estimated 20-28 hours of effort, assigned section ownership, and created a weekend sprint action — all before reading the actual POC document. When DAF shared it, it was 20 sections (not 8), execution-ready (not a framework), and already drafted (not needing creation).

## Three Correlated Failures

1. **Built a plan before reading the document.** I assessed readiness at 38% against an 8-section framework that DAF had already exceeded with a 20-section draft. My assessment solved the wrong problem.

2. **Projected urgency DAF didn't feel.** "Weekend panic sprint," "Fuad hasn't responded yet," "you may need to follow up before the weekend starts." DAF's reality: no hard deadline, document exists, validation is the gate, ready when it's right.

3. **Over-filed.** 3 intelligence records, 1 conversation record, 1 action record, 2 memory notes for what was essentially: read an email thread, read a document, cross-reference against the spec, report findings. The filing overhead was disproportionate to the analytical output.

## Root Cause

Defaulted to producing output before consuming input. The instinct to "do something" overrode the discipline to "read first."

## Corrective Action

When DAF references an existing document, artefact, or deliverable:
1. **Request to read it** before producing any assessment, plan, or framework
2. **Read first. Assess second. Always.**
3. **File proportionately** — a single validation report may need only 1 record, not 5

## Trigger

DAF says "I already have the document" or references an existing artefact I haven't seen.

## Response

"Send it to me." Not "let me re-engineer the framework."
