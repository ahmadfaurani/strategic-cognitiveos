## STEP 3 — CORRELATE

### Cross-Signal Correlations

**C1: The Enforcement Gap Chain**
```
S1 (ACT schema enforced) → S4 (17 other schemas NOT enforced) → same schema drift pattern accumulating silently
```
The ACT fix proved `additionalProperties: false` works. But it's a point fix. Every other record type (DOC, LSN, INT, DEC, INIT, RSK, etc.) still accepts arbitrary fields without blocking. The pattern that produced 18 non-schema fields in ACT is active in 17 other record types right now.

**C2: The Identity Resolution Chain**
```
S5 (DAF vs faurani-jaafar) → S8 (STK IDs and team names as assignee) → cross-record linking breaks
```
If owner="DAF" in 5 records and owner="faurani-jaafar" in 99 records, queries for DAF's actions return 99, not 104. Same for "Ember" vs "ember", "Amelia Nadia" vs "amelia-nadia". The naming inconsistency means any analytics or filtering by person is silently incomplete.

**C3: The Staleness Chain**
```
S6 (86 draft records) → S7 (20 placeholder completion_evidence) → records exist but operational value unclear
```
86 records in draft status represent work that was captured but never advanced. 20 completed records have placeholder evidence — they're marked done but the proof is "retroactively added during schema formalization", not real verification. The ACT system tracks activity but not outcomes.

**C4: The Semantic Redundancy Chain**
```
S9 (attention_level "high" × 71 + priority "high" × 94) → two fields encoding similar information
```
The schema has both `priority` (critical/high/medium/low) and `attention_level` (immediate/critical/high/medium/low/monitored/strategic/deferred). 71 records have attention_level="high" AND 94 have priority="high". The fields overlap but are not identical — creating ambiguity about which is authoritative for prioritisation.

## STEP 4 — PATTERN RECOGNITION

### Patterns Detected (Doctrine §6 Reference)

**P1 — Point Fix Pattern (§6.8 Execution Drift variant):** The ACT schema formalization is a point fix — it solved one record type completely but didn't propagate the solution system-wide. This is the same pattern as the earlier schema audits: fix one type, leave others. The fix is correct; the scope is incomplete.

**P2 — Naming Drift (§6.8):** Owner and assignee fields have inconsistent naming: "DAF" vs "faurani-jaafar", "Ember" vs "ember", "Hadri" vs "hadri", "Amelia Nadia" vs "amelia-nadia". This is the data-layer equivalent of the governance drift found in LSN-20260821-005 — the same concept, different identifiers.

**P3 — Staleness Accumulation (§6.6 Decision Debt variant):** 86 draft records (58%) represent captured-but-unadvanced work. Without a staleness sweep mechanism, drafts accumulate indefinitely. This is structural: the intake pipeline creates records but there's no lifecycle enforcement for drafts that never progress.

**P4 — Evidence Debt (§6.7 Coordination Debt variant):** 20 completed records have placeholder completion_evidence. The field exists, the status is "completed", but the evidence is synthetic. This is evidence debt — the closure discipline was retroactive, not contemporaneous. Future completions must have real evidence at time of completion.

**P5 — Schema Redundancy (§6.9 Portfolio Collision variant):** `attention_level` and `priority` encode overlapping information. When two fields serve similar purposes without clear delineation, operators use them inconsistently. This is schema-level redundancy — the portfolio collision pattern applied to field design.

## STEP 8 — LEARN

### Learning Extraction

#### Learning 1: Point Fix ≠ System Fix

**Observation:** The ACT schema formalization solved one record type completely (33 properties, additionalProperties: false, 148/148 T1/10/10). But 17 other schemas still lack additionalProperties: false. The same schema drift pattern that produced 18 non-schema fields in ACT is accumulating in every other record type.

**Lesson:** A schema fix applied to one record type is a point fix, not a system fix. When a pattern is identified and fixed in one type, immediately audit all other types for the same pattern. The cost of replication is low (add one line per schema); the cost of not replicating is silent accumulation.

**Institutionalisation:** When any schema is formalized, the same day: (1) audit all other schemas for the same gap, (2) flag the gap, (3) commit to a replication timeline. Schema formalization is not complete until it's system-wide.

#### Learning 2: Schema Formalization Exposes Hidden Data Quality Issues

**Observation:** The formalization process exposed 7 data quality issues that were invisible before the audit: naming inconsistency, non-person assignees, placeholder evidence, empty arrays, semantic redundancy, draft staleness, and STK-ID-as-assignee.

**Lesson:** Schema formalization is a diagnostic tool, not just a corrective one. The act of defining what's valid reveals what's wrong. Future formalization efforts should explicitly plan for data quality discovery, not just field migration.

**Institutionalisation:** Add a "Post-Formalization Data Quality Audit" step to the Engineered Success Framework. After schema formalization, always run: (1) value distribution analysis, (2) naming consistency check, (3) empty/null analysis, (4) semantic overlap check.

#### Learning 3: Retroactive Evidence Is Not Evidence

**Observation:** 20 completed records received placeholder completion_evidence ("retroactively added during schema formalization"). This satisfies the schema but not the semantic intent — the evidence doesn't prove the action was completed, it proves the field was missing.

**Lesson:** Retroactive evidence is structural compliance, not operational truth. When evidence is added retroactively, it should be marked as such (not presented as contemporaneous). The field `completion_evidence` should distinguish between "evidence recorded at time of completion" and "evidence added after the fact."

**Institutionalisation:** When retroactively adding evidence, always use explicit marker text. Consider a `completion_evidence_type: contemporaneous | retroactive` field for future schema versions.

#### Learning 4: attention_level and priority Need Semantic Delineation

**Observation:** The ACT schema has both `priority` (critical/high/medium/low) and `attention_level` (immediate/critical/high/medium/low/monitored/strategic/deferred). 71 records have attention_level="high" and 94 have priority="high". The overlap creates ambiguity.

**Lesson:** When two fields encode similar information, operators use them inconsistently. Either merge them or define clear semantic boundaries. Proposed distinction: `priority` = importance (how much does this matter?), `attention_level` = urgency (how soon does this need attention?). "Critical priority + deferred attention" = important but not urgent. "Medium priority + immediate attention" = urgent but not important.

**Institutionalisation:** Document the semantic distinction in the schema description and the template. If the distinction isn't useful in practice, merge the fields.

#### Learning 5: The Cognitive Loop Itself Adds Value

**Observation:** Running the 8-step loop on the completed ACT formalization produced 5 findings that the formalization process itself didn't surface. The formalization was execution (schema → template → migration → validation). The Cognitive Loop is reflection (what did we miss? what did this expose? what should we do next?).

**Lesson:** Execution and reflection are different activities. Execution completes the task. Reflection extracts the learning. Both are necessary. Neither is sufficient alone. The Cognitive Loop should be run after every major formalization, not just when DAF requests it.

**Institutionalisation:** Add "Cognitive Loop post-execution review" as a mandatory step in the Engineered Success Framework. After Definition of Done is met, run the 8-step loop to capture learnings before they're lost.
