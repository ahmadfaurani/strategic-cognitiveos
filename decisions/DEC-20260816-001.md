# Context

DAF transmitted ADEP-001 (Agentic Diligence Execution Protocol: Diligence, Verification, Operationalisation & Engineered Success Doctrine) as a Core Governance Instruction applicable to all agents, sub-agents, workflows, decisions, research activities, operational tasks, strategic initiatives, and generated artifacts.

ADEP-001 is a 47-section execution doctrine that governs HOW work is executed — sitting above the CognitiveOS Prime Doctrine (DEC-20260815-003), which governs WHAT work is done and the analytical methods used. Together they form a two-layer governance architecture:

- **ADEP-001 (execution layer):** Diligence, verification, execution lifecycle, process maturity, completion standards, evidence requirements
- **CognitiveOS Prime Doctrine (cognitive/analytical layer):** Cognitive loop, pattern recognition, intelligence standards, prioritisation, engineered success framework, objective decomposition

The protocol was received in two transmissions: partial (§1-§3 partial, ending mid-sentence at State 3) at 01:37 UTC, and complete (§3 completion through §47) immediately following. This record documents the adoption and operationalization of the complete protocol.

# Decision

Adopt ADEP-001 as a Core Governance Instruction with immediate effect. All agents, sub-agents, workflows, decisions, research activities, operational tasks, strategic initiatives, and generated artifacts are subject to its provisions.

ADEP-001 takes precedence over speed, superficial completeness, and performative productivity whenever those objectives conflict, per §47 (Supreme Rule).

# Rationale

1. **Anti-equivalence principle gap:** CognitiveOS doctrine addresses analytical rigour (§5-§10) but does not explicitly govern the execution discipline gap between "output produced" and "outcome achieved." ADEP-001 §1 fills this with 8 anti-equivalence principles.

2. **Process maturity model gap:** CognitiveOS had no explicit model for tracking whether a process is Expressed → Codified → Institutionalised → Operationalised. ADEP-001 §3 provides this. The Cross-Doctrinal Analysis SOP (institutionalized 2026-08-16) is currently at State 3 (Institutionalised) but NOT yet State 4 (Operationalised) — it has not yet been used for a second cycle.

3. **Diligence classification gap:** CognitiveOS had no proportional diligence framework. ADEP-001 §5 introduces D1-D4 levels matching consequence to verification depth. This directly improves resource allocation for verification activities.

4. **Execution lifecycle gap:** CognitiveOS §5 (Cognitive Loop) is a sense-think-act loop, not an execution lifecycle. ADEP-001 §6-§17 provides an 11-phase execution lifecycle that encompasses and extends the Cognitive Loop.

5. **Completion standards gap:** CognitiveOS had no explicit "Definition of Done" or closure gate. ADEP-001 §23, §24, §44 provide three layers: task completion, evidence-backed completion, and closure gate.

6. **The governing question (§1) directly extends CognitiveOS §25 (Daily Operating Question):**
   - CognitiveOS: "What are the three actions the Operator can take now?"
   - ADEP-001: "What must be true for this objective to actually succeed, and what evidence confirms that those conditions are true?"
   - Together: What must be true → What actions make it true → What evidence confirms it worked.

# Alternatives Considered

1. **Merge ADEP-001 into CognitiveOS Prime Doctrine as additional sections** — Rejected. ADEP-001 is a distinct doctrine with different scope (execution discipline vs cognitive/analytical method). Merging would blur the boundary and make updates harder. Two-layer architecture is cleaner.

2. **Adopt selectively (cherry-pick sections)** — Rejected. ADEP-001 is designed as an integrated system. §47 explicitly states it "takes precedence over speed, superficial completeness, and performative productivity whenever those objectives conflict." Selective adoption would violate the doctrine's own principles.

3. **Treat as advisory guidance** — Rejected. ADEP-001 §1 states "You MUST apply sufficient diligence proportional to the consequence of failure." The MUST is normative. Treating it as advisory would be an anti-pattern per §37 (checkbox completion, premature closure).

4. **Defer adoption pending pilot** — Rejected. ADEP-001 is a governance instruction from DAF (authority). The protocol's own §4 (Process Completion Rule) states that the correct status must be reported — deferring adoption would be reporting "designed" when the correct status is "approved but not yet operationalised."

# Assumptions

- ADEP-001 sits alongside (not replacing) CognitiveOS Prime Doctrine — confirmed by scope analysis (execution layer vs cognitive/analytical layer)
- ADEP-001 applies to Ember (primary agent) and all spawned sub-agents — confirmed by §18 (Sub-Agent Governance)
- The 11-phase execution lifecycle (§6-§17) does not replace the 8-step Cognitive Loop (CognitiveOS §5) but wraps it — the Cognitive Loop operates within Phase 9 (Execution Discipline) and Phase 11 (Failure Mode Analysis)
- Diligence levels D1-D4 map to existing CognitiveOS record types: D1=routine operational, D2=action records, D3=intelligence/decision records, D4=war-room/critical risk records

# Expected Outcome

1. All agent execution follows the 11-phase lifecycle (§6-§17)
2. All significant tasks classified D1-D4 with proportional verification
3. Process maturity tracked across 4 states for every governance artifact
4. Completion claims backed by evidence per §24
5. Closure gate (§44) applied before declaring success on any major initiative
6. Anti-patterns (§37) actively detected and resisted in all outputs
7. Execution state reporting (§41) used for substantive workflow updates to DAF

# Consequences

- **Immediate:** All active and pending work items must be assessed against ADEP-001 standards
- **Operational:** Reporting format for workflow updates changes to §41 standard (Objective, Current State, Completed, In Progress, Blocked, Risks, Decisions Required, Next Critical Actions, Success Confidence, Confidence Basis)
- **Governance:** ADEP-001 is added to pre-commit hook governance file list
- **SOPs:** Intake SOP, Template Discipline SOP, and Cross-Doctrinal Analysis SOP must be updated to reference ADEP-001
- **CognitiveOS doctrine:** §50 or new section should reference ADEP-001 as the execution layer
- **Sub-agent orchestration:** All future sub-agent spawns must include §18 required fields (precise objective, bounded scope, authority limitations, etc.)
- **Closure:** CyberDSA 2026 initiative cannot be declared "closed" without passing §44 closure gate

# Risks Accepted

- **Adoption curve risk:** Full internalization of 47 sections will take multiple execution cycles. Mitigated by: applying §46 (20-step Master Agent Execution Directive) as the operational shortcut.
- **Overhead risk:** D3/D4 requirements add verification overhead to strategic tasks. Accepted: ADEP-001 §5 explicitly states "When uncertain between two diligence levels, apply the higher level."
- **Layer interaction risk:** Potential confusion between ADEP-001 execution lifecycle (§6-§17) and CognitiveOS Cognitive Loop (§5). Mitigated by: clear scope separation (execution vs analysis) documented in this decision record.
