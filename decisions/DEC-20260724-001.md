# Context

AI-assisted work produces significant knowledge (conversations, decisions, analyses) that is lost across sessions. Existing memory files (MEMORY.md, daily notes) provide continuity but lack schema validation, cross-referencing, and structured retrieval. DAF specified a tool-independent memory standard that survives platform changes and enforces data discipline.

# Decision

Build the Personal Intelligence Operating System with the following architecture:

**Platform Roles:**

| Platform | Role | Authority |
|----------|------|-----------|
| GitHub | Canonical records, schemas, standards | Authoritative |
| Obsidian | Knowledge navigation, backlinks | Contextual |
| Notion | Projects, tasks, stakeholders | Operational |
| AI Layer | Extraction, tagging, retrieval | Processing |
| Human Owner | Validation, judgement, decisions | Final Authority |

**Phase 1 Foundation (36 files):**

- 4 governance documents (operating principles, classification, lifecycle, contribution)
- 4 JSON schemas (memory-card, decision, action, stakeholder)
- 4 YAML taxonomy files (tags, statuses, priorities, sensitivity)
- 6 Markdown templates (conversation, decision, insight, action, project, stakeholder)
- Full directory tree with index files
- README.md and CHANGELOG.md

**Key Design Principles:**

1. Standard permanence — standards outlive tools
2. GitHub as canonical authority
3. Human validation is final authority
4. Controlled taxonomy (no free-tagging)
5. Record lifecycle with supersession discipline
6. Schema-validated records
7. Information classification (public/internal/confidential/restricted)

# Rationale

- Existing memory works but doesn't scale — 29K+ chars in MEMORY.md, hard to search structurally
- Tool-independent design means the system survives if OpenClaw, Obsidian, or Notion changes
- Schema validation prevents drift and enforces completeness
- Controlled taxonomy prevents tag explosion and inconsistency
- GitHub as authority provides versioning, collaboration, and durability

# Alternatives Considered

- **Obsidian vault as primary store** — Use Obsidian with frontmatter as the main system. Rejected: Obsidian is great for navigation but weak for schema validation, programmatic access, and CI/CD. GitHub is more durable and tool-independent.
- **Notion as primary store** — Use Notion databases for all records. Rejected: Notion is operational, not canonical. API limits, vendor lock-in, and data portability concerns. Better suited for project/task management.
- **Extend MEMORY.md with structured sections** — Keep the current file-based approach but add more structure. Rejected: No schema enforcement, no cross-referencing, no validation. Doesn't solve the core problem.

# Assumptions

- GitHub remains accessible and stable for the foreseeable future
- DAF maintains the GitHub account (ahmadfaurani) long-term
- Schema changes follow the contribution standard (7-step workflow)

# Expected Outcome

A structured, schema-validated knowledge management system with 36 foundation files that survives platform changes and scales beyond individual memory files, enabling structured retrieval, cross-referencing, and data discipline across all AI-assisted work.

# Consequences

- All future knowledge capture should follow PI-OS standards
- MEMORY.md continues as OpenClaw-specific operational memory; PI-OS is the structured layer
- Week 2 pilot capture validates the schemas against real data
- Taxonomy gaps discovered during pilot will be addressed in Week 4

# Risks Accepted

- **Adoption friction — too much overhead** (medium severity) — Mitigation: Start small (pilot), automate where possible
- **Schema rigidity prevents quick capture** (medium severity) — Mitigation: Templates are guides, not rigid forms; allow manual entries with later validation
- **GitHub repo privacy/security** (high severity) — Mitigation: Private repo, .gitignore for secrets, sensitivity classification enforced
- **Duplication with MEMORY.md** (medium severity) — Mitigation: MEMORY.md is operational; PI-OS is canonical. Different purposes.
