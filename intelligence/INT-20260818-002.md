# Intelligence Record

## KKOM System Overview

**KKOM** = GovComms Command Center — the live system that operationalises the R.I.S.I.K doctrine.
**RISIK** is the doctrine (methodology). **KKOM** is the system (technology).

## Current State (Static Prototype — COMPLETED)

- 8 HTML screens at mock-up-db-kkom-0752.myrisik.duckdns.org
- Manually typed data
- No database, no back-end, no API
- Reports generated outside the system
- No inter-system connectivity

## Target State (Full System)

- Live data, auto-updating
- Back-end + database
- API + API documentation
- Reports generated from within the system
- Inter-system integration capability

## 7-Step Development Pathway

1. **Modul RISIK** — 70+ page doctrinal document (source of truth)
2. **Static HTML Pages** — ✅ COMPLETED — 8 prototype screens
3. **Decision: Upgrade to Full System** — static → live (front-end + back-end + API docs)
4. **Knowledge Transfer Before Building** — doctrine training for developers, paired with internal technical team
5. **Phased Building** — TULIS → BINA → SEMAK → LULUS cycle per stage
6. **Full Integration & UAT** — end-to-end testing on real data
7. **Delivery** — live system + API docs + handbook + ongoing support

## 5-Stage Build Sequence (Dependency-Ordered)

| Stage | What's Built | RISIK Team Reviews |
|-------|-------------|-------------------|
| 1. Data Foundation | Schema, database, terminology dictionary, codebook | Every field matches module. No developer-invented terms. |
| 2. Back-end + API | Collection & computation engine, API docs | Computation matches doctrine. API docs written WITH code. |
| 3. Front-end | 8 prototype screens upgraded to live data | Screens display doctrine meaning, not just pretty. |
| 4. Reports & Export | Colour PDF, auto-email, archive | Reports from system, no manual external work. |
| 5. Full Integration | All components talking | End-to-end on real data, not sample data. |

## TULIS → BINA → SEMAK → LULUS Governance Cycle

| Phase | Owner | What Happens |
|-------|-------|-------------|
| TULIS (Write) | RISIK team (Prof Suhaimee + doctrine team) | Define what to build, boundaries, acceptance criteria |
| BINA (Build) | Developer + internal technical companion | Build together. Companion present throughout. |
| SEMAK (Review) | RISIK team + internal technical team | Doctrine-correct? Reviewer tests personally. |
| LULUS (Pass) | RISIK team — final say | Written decision with reasons. |

### Two Return Types (Critical Distinction)
- **BAIKI (Fix)** — Instructions correct, implementation wrong → developer fixes
- **TULIS SEMULA (Rewrite)** — Instructions wrong → build stops until new instructions ready
- **Don't mix them** — sending work back to developer when the problem is in the instructions wastes time

## Three Governing Rules
1. No building before writing — every stage starts with written spec and acceptance criteria
2. No approval by demo alone — reviewer tests personally; showing screens is not proof
3. Decisions must be written with reasons — otherwise next stage repeats same errors

## Critical Assumption
The diagram assumes: (1) the 8-screen static prototype is the accepted design reference, and (2) the internal technical team has capacity to companion the developer throughout — not just at review meetings. If companioning capacity doesn't exist, step 4 becomes decoration and doctrine error risk returns in full.

## Roles

| Party | Role |
|-------|------|
| Prof Suhaimee & RISIK team | Doctrine owner. Writes specs, passes/rejects. Final say on doctrine. |
| Internal technical team | Trains developer. Sits beside developer throughout. Reviews technical before RISIK team. |
| Developer | Builds front-end, back-end, API docs. Asks early when unsure. |
| User representative | Tests per real workflow at integration stage. |
